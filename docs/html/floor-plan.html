Floor plan generator and designer

A drawn plan per dining area: generate a draft, change it, save versions, publish. Waiters see the published plan on Service (ADR 0073). Code: packages/shared/src/floor-plan/, apps/api/src/modules/pos/floor-plans.*, apps/web/components/tables/plan/, apps/web/lib/pos/plan-editor.ts. Spec: docs/modules/pos.md → Step 8.

Data model

dining_areas
 └─ pos_floor_plan_versions       append-only; version per area, layout (JSON, at most 100 kB), restored_from
     └─ pos_floor_plan_publications   append-only; the newest one is live
  • A version outlives its area: an empty area can be deleted, its history stays (no foreign key on area_id).
  • The layout: a room (longer side 1000 units, the same unit both ways), up to 100 tables and 100 pieces (wall, door, bar, decor), whole numbers, everything inside the room.
  • A table in the layout is an existing one (tableId) or a new one (name, seats, shape) that is created on Publish.
  • Positions on dining_tables are not touched. A rollback shows the old positions.

Technical flow

Generate

  1. Browser onlyRoom in metres, tables in all, seats and shape of new tables.
  2. generateFloorPlan (pure)Even rows, at least 1.2 m between tables and 0.6 m to the walls. Existing tables first, in their order; new names go on with the area's numbering.
  3. ResultA draft in the designer (one undo step), or "Room for N tables of this kind". Nothing is saved.

Save

  1. Designer → APIPOST /pos/areas/:id/floor-plan/versions { baseVersion, layout }
  2. APILocks the area. A newer version exists → 409 pos.floor_plan_changed. A table that is not in the area or out of service → 409 pos.floor_plan_table_invalid.
  3. APIWrites the next version. Audit pos.floor_plan.saved (counts only).

Publish

  1. Designer → APIPOST /pos/areas/:id/floor-plan/publish { version }
  2. API, one transactionCreates the new tables (audited like any new table) and a version that names them. A taken name → 409 pos.table_name_taken and nothing happens.
  3. APIWrites the publication: this version is live. Publishing the live version again writes nothing.
  4. Service and TablesService asks for live plans every 5 minutes and on load. Tables that left the area or are out of service are not drawn.
RoutePermission at the area's location

Owner, admin and manager can edit; waiter and cashier look. Feature pos. All writes are idempotent.

Known gaps

  • No rotation, several floors, live editing by two people, background image or host screen.
  • On phones Service can scroll 10 px sideways when a table has a long name (list tile, older than this feature).
  • A change to a published plan reaches an open Service screen within 5 minutes.
