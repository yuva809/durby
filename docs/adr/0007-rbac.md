# ADR 0007: Roles, permissions, route markers and invitations

- Status: accepted
- Date: 2026-10-23
- Step: Phase 1.3 (memberships + RBAC)

## Context

Step 1.2 authenticates every non-public route but authorizes nothing: memberships have no role, and a route without a
marker only needs a valid token. Step 1.3 adds roles, permission keys, location scope and invitations, and makes
rule 10 enforceable at boot. Spec: [docs/platform/rbac.md](../platform/rbac.md).

## Decisions

1. **Permission registry in code** (`packages/shared/src/permissions.ts`), keys `module.entity.action`, each with a
   scope (`organization` | `location`). The API validates role keys against it; the database checks only the key
   shape (the registry isn't in the database). Unknown keys in stored rows are ignored when resolving (fail closed).

2. **System role permissions are fixed in code**, the same for every organization. Owner holds every registered key,
   so new modules need no data migration for it. Admin, Manager and Staff list every key as granted or denied; an
   unlisted key fails the typecheck and a test, so adding a key forces a decision per role.
   **Consequence: changing a system role's permissions changes it for all organizations at once**, in a deploy.
   Organizations that need different sets create custom roles (`role_permissions` rows). System roles cannot be
   edited or deleted.

3. **Location scope as rows, not arrays.** `memberships.all_locations` plus `membership_locations (tenant_id,
membership_id, location_id)` with composite FKs; arrays can't have foreign keys. "Not all, no rows" means no
   locations. Location delete is `RESTRICT` so it can't silently widen a membership. Organization-scope keys need
   `all_locations = true`.

4. **Permissions are resolved per request from the database**, not carried in the JWT, so role changes apply at once.
   Cost: one indexed tenant query per permission-checked request (cached for the request in CLS). A Redis cache can
   come later behind `AccessService` if needed.

5. **One global guard, four markers, checked at boot.** `AccessGuard` replaces `AuthGuard` as the only `APP_GUARD`
   (explicit order instead of relying on provider registration order) and applies exactly one of `@Public`,
   `@Authenticated`, `@RequirePermission`, `@PlatformOnly`. The api refuses to boot if any route has zero or several
   markers or an unregistered key. `@PlatformOnly` means Durby platform staff (operators across tenants); that isn't
   modelled yet, so it denies every request until it is (its own ADR).

6. **No privilege escalation.** A user can only grant keys they hold, only an Owner can assign or change an Owner,
   members can only manage members whose role is a subset of their own, and nobody can change or remove their own
   membership (a "leave organization" flow comes later). The last Owner is protected twice: a row lock + check in the
   service (clean 409) and a deferred constraint trigger that takes the same lock (backstop against races and future
   code paths).

7. **Ending access on removal** (1.2 TODO): a per-organization marker `auth:revoked:org:<orgId>:<userId>` next to the
   existing session and user markers, read in the same `MGET`. Narrower than `auth:revoked:user`, which would sign the
   user out of every organization.

8. **Invitation tokens carry the org id: `<orgId>.<secret>`.** The accept endpoints are public (or user-level) and
   only receive the token, while `invitations` is a tenant table under RLS. The org id is parsed as a UUID, then the
   lookup runs as `TenantContext.run({ tenantId: orgId })` and must match the secret's hash under RLS.
   **This is a narrow exception to rule 1** (tenant from the session): here the token _is_ the credential, like the
   refresh cookie, and the claimed org is trusted only after the hash matched — the same pattern as
   `MembershipLookup.isMember` in ADR 0006. A forged org id finds nothing; unknown org, wrong secret, expired, used and
   revoked all answer the same `400 auth.token_invalid`, and the endpoints are rate limited.
   _Rejected:_ a `SECURITY DEFINER` lookup by token hash — a second cross-tenant function with caller-supplied input,
   for no gain over the RLS-scoped lookup.

9. **No account enumeration towards the inviter.** Same response and mail whether or not the invited email has an
   account. The token holder (proven inbox access) may learn it, since they must either set a password or sign in.
   The public accept never touches an existing account (409 `invitations.sign_in_required`).

10. **Users stay auth-private** (ADR 0006): `platform/auth` exports a `UserDirectory` for the few reads and the one
    write RBAC needs. `ProvisioningService` moves to `platform/provisioning`, which depends on auth and rbac, so
    creating an organization always creates its system roles without a dependency cycle.

11. **Expand/contract for `memberships.role_id`**: nullable now, backfilled to Owner for existing memberships in the
    migration, `NOT NULL` in a later step. The backfill runs per organization with `app.tenant_id` set, so `FORCE RLS`
    stays on; it runs before the last-Owner trigger is created.

12. **Rules 8 and 9 until 1.4 / 1.9:** structured `security` log events for role, permission, membership and
    invitation changes. `Idempotency-Key` for the RBAC write endpoints is deferred to platform/idempotency (1.9); the
    routes are listed in the spec. Accept endpoints consume a single-use token and are exempt like auth.

## Amendment (2026-10-23): active role and permissions in the session

The session body (login, refresh, switch-organization) and `GET /auth/me` carry `activeRole` and `activePermissions`:
the caller's role (system key or custom role name) and effective permission keys in the token's active organization.
The home page shows the role; step 1.10 filters navigation by the keys.

- **Narrow exception to rule 10** for these `@Authenticated()` / public auth routes: they read only the caller's own
  membership in the token's active organization, through the tenant client under RLS
  (`TenantContext.run({ tenantId: activeOrg, userId: caller })`). No organization → `null` / `[]`. Never another user's
  or another organization's membership (tested).
- **UI hints only.** They can be stale until the next refresh or switch; the api still resolves and checks every
  permission per request (decision 4). Nothing on the server reads them back.
- **No dependency cycle.** platform/auth defines an `ACTIVE_ACCESS_LOOKUP` token; platform/rbac provides it on top of
  `AccessService`. Auth never imports rbac.

## Consequences

- Every new route needs a marker or the api doesn't start; every new permission key needs a decision for each
  non-Owner system role.
- One extra query per permission-checked request; one extra Redis key per authenticated request.
- A later step makes `memberships.role_id NOT NULL` once no deployed release inserts memberships without a role.
- Changing system-role permissions is a product decision that affects every tenant.
