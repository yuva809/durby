# ADR 0004: Staging deployment

- Status: accepted
- Date: 2026-10-21
- Step: Phase 0.4 (staging deploy)

## Context

Step 0.4 needs a staging environment that serves the web app and reports DB + Redis health, with migrations as a
release step and structured logs. The phase plan suggested a managed platform (Render/Railway/ECS). We have a
Hetzner Cloud CPX22 (2 vCPU, 4 GB RAM, 80 GB NVMe, Ubuntu) and want low, predictable cost and full control over the
Postgres role setup from ADR 0002.

## Decisions

1. **Single Hetzner server with Docker Compose** (`infra/staging/`, project `durby-staging`, in `/opt/durby`)
   instead of a managed platform. Postgres 18, Redis 8, api, web and Caddy run as containers. No Kubernetes, no Swarm.
   The server **never builds images**: it only pulls from GHCR.
2. **Images** (`apps/api/Dockerfile`, `apps/web/Dockerfile`): multi-stage, `turbo prune` + `pnpm deploy`,
   `node:22-alpine`, non-root `node` user, `tini`, image healthchecks. Three images per commit, tagged with the full
   git SHA (plus a moving `staging` tag):
   - `durby-api` (runtime only; Prisma's runtime trimmed to the Postgres query compiler),
   - `durby-api-migrate` (Prisma CLI + migrations; runs `prisma migrate deploy` as the release step). It is large
     (~1 GB, it carries the CLI's dev dependencies) but only runs during deploys,
   - `durby-web` (Next.js `output: 'standalone'`).
     CI builds all three on every PR without pushing, so a broken Dockerfile fails the PR.
3. **Network exposure:** only Caddy publishes ports (80, 443/tcp+udp). Postgres and Redis are on an `internal`
   Docker network with no route in or out. Host firewall (ufw) allows 22/80/443 only; a Hetzner Cloud Firewall with
   the same rules covers the fact that Docker-published ports bypass ufw.
4. **Caddy** terminates TLS (Let's Encrypt) for `staging.durby.tech`, routes `/api/*` to the api and everything else
   to web, sets `X-Request-Id` to its own per-request UUID (overwriting client values) and logs it as `request_id`.
   Query strings are redacted from access logs. **Basic auth protects the web routes only, not `/api/*`**: it would
   clash with the `Authorization: Bearer` token introduced in step 1.2. **Revisit in 1.2** (e.g. drop basic auth
   once real sign-in exists, or move it to an IP allowlist).
5. **Database roles** match ADR 0002: `infra/staging/postgres-init/01-roles.sh` creates `durby_migrator` (owner,
   **NOCREATEDB**) and `durby_app` on the first start, with passwords from the server-side `.env` (read via psql
   `\getenv`, never in argv). The api only receives `DATABASE_URL` (durby_app); only the `migrate` container
   receives `MIGRATION_DATABASE_URL`. Postgres is tuned for ~1 GB (`shared_buffers=256MB`,
   `effective_cache_size=768MB`, `max_connections=50`).
6. **Secrets** live only in `/opt/durby/.env` (mode 600, owner `deploy`), generated by `server-setup.sh` with
   `openssl rand`. Nothing secret is committed; `infra/staging/.env.example` is the template.
7. **Deploys via GitHub Actions over SSH** (`.github/workflows/deploy-staging.yml`), triggered by `workflow_run` of CI,
   only when `conclusion == success`, `head_branch == main` and `event == push`. The workflow checks out and tags
   `workflow_run.head_sha`, never the current `main`. It uses a `staging` GitHub Environment with the SSH key and a
   **pinned host key** as secrets. The server logs in to GHCR with the job's short-lived `GITHUB_TOKEN` (via stdin)
   and logs out after the deploy; no long-lived registry credential is stored on the server.
   `workflow_dispatch` with a SHA redeploys or rolls back an already-built release without rebuilding.
8. **Two health endpoints.** `/api/v1/health/live` (process only) is the Docker healthcheck and the "is the new api
   up" gate in `deploy.sh`, so a database blip never marks the container unhealthy or blocks a rollback.
   `/api/v1/health` (database + Redis, 503 when degraded) is checked through Caddy after each deploy (status `ok` and
   `version` equal to the deployed SHA) and is the endpoint for monitoring.
9. **Release step order** (`bin/deploy.sh`): pull → Postgres/Redis healthy → `migrate` → new api/web healthy →
   Caddy reload. A failed migration leaves the old release running; an unhealthy new release is replaced by the
   previous one automatically. **Rollbacks skip migrations**, so migrations must stay backward compatible with the
   previous release (expand/contract; rule added to CLAUDE.md). Images of the last 5 releases stay on the host.
10. **Backups:** nightly (`systemd` timer, 03:00 UTC) `pg_dump --format=custom` as the Postgres superuser, encrypted
    with **age** to a public key whose private key is kept off the server, copied to a **Hetzner Storage Box** with
    **rclone** (SFTP, key auth, pinned host key). 7 days retention locally and remotely. `bin/restore.sh verify`
    restores into a scratch database for drills; `restore.sh live` replaces the staging database.
11. **Logging:** `nestjs-pino`. JSON in production, pretty in development, `LOG_LEVEL` env var. Each request has an id
    (a well-formed incoming `X-Request-Id`, else a UUID v7), echoed in the response. Serializers log method, path
    (without query string) and status only: never headers, cookies or bodies. Common secret field names are redacted
    as defense in depth. Docker rotates container logs (10 MB × 5).
12. **Server hardening** (`infra/staging/server-setup.sh`, run by a human as root): key-only SSH, no root login,
    `AllowUsers`, a non-root `deploy` user for CI (docker group, restricted key, no sudo), unattended security updates
    with automatic reboot at 04:30, 2 GB swap, `vm.overcommit_memory=1` for Redis. Containers run with
    `no-new-privileges`, dropped capabilities, memory limits, and read-only root filesystems for api and web.

## Consequences

- Staging is a single point of failure with no automatic failover; acceptable for staging. A production setup will
  need its own ADR (managed or replicated Postgres, off-site monitoring, zero-downtime deploys).
- A deploy briefly restarts api and web (seconds). Caddy retries are not configured.
- `deploy` in the `docker` group is root-equivalent on the server; the SSH key is the crown jewel and lives only in
  the GitHub `staging` environment.
- The Next.js `/api/v1` rewrite from ADR 0001 is baked at build time (`API_URL=http://api:4000`), but in staging
  Caddy routes `/api/*` directly, so the rewrite is only used in local development. This resolves the "revisit in
  0.4" note in ADR 0001.
- The api now needs Redis at boot (like Postgres); integration tests start a Redis Testcontainer.
- The staging Compose project is named `durby-staging` so it never shares containers or volumes with the local dev
  project (`durby`) on a developer machine.
